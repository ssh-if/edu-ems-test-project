## 一、性能测试背景与目标

### 1.1 项目背景
紫薇教育 V2.0 版本计划在广西全区 30+ 校区推广，注册用户 5 万+，日活用户预计 1.2 万。
- **开学季业务高峰**：8月25日-9月5日 报名缴费集中
- **日常高峰时段**：工作日 10:00-11:30（财务对账）、19:00-21:00（家长小程序缴费查课表）

### 1.2 性能测试目标（客户SLA 合同约定）
| 指标 | 性能目标（可接受） | 期望（优秀） |
|------|--------------------|--------------|
| **登录接口 TPS** | ≥ 200 | ≥ 500 |
| **登录接口 P95 响应时间** | ≤ 2 秒 | ≤ 1 秒 |
| **报名缴费接口 TPS** | ≥ 200 | ≥ 400 |
| **报名缴费接口 P95 响应时间** | ≤ 3 秒 | ≤ 1.5 秒 |
| **财务报表查询 TPS** | ≥ 50 | ≥ 100 |
| **财务报表查询 P95** | ≤ 5 秒 | ≤ 3 秒 |
| **学员列表搜索 TPS** | ≥ 300 | ≥ 600 |
| **500 并发 10 分钟错误率** | ≤ 0.1% | ≤ 0.01% |
| **服务器 CPU 峰值** | ≤ 80% | ≤ 70% |
| **JVM Full GC 频率** | ≤ 1 次 / 10min | 0 次 |

### 1.3 测试类型
| 类型 | 说明 |
|------|------|
| 基准测试（Baseline） | 单用户 1 次，获取基准响应时间，做对比参考 |
| 负载测试（Load） | 逐步加压至预期并发，观察系统在容量下的表现 |
| 压力测试（Stress） | 超过预期并发 2-3 倍，看系统极限和崩溃恢复 |
| 稳定性测试（Soak） | 70% 负载 × 24 小时 内存泄漏/句柄泄漏检测 |
| 并发测试（Concurrency） | 关键业务点（下单扣减）1000 线程同时请求 测数据一致性 |
| 异常测试（Failover） | 压测中 Kill 一个应用节点，看是否自动恢复切换 |

## 三、性能测试场景设计

### 3.1 业务场景配比（贴合真实运营数据）
| 编号 | 业务场景 | 接口/操作 | 占比 | 压测目标 |
|------|----------|-----------|------|----------|
| SC-01 | 用户登录 | POST /api/auth/login | 15% | P95 ≤2s |
| SC-02 | 学员列表+搜索 | GET /api/student/list | 20% | P95 ≤1s |
| SC-03 | **报名缴费查询** | GET /api/enrollment/list | 15% | P95 ≤2s |
| SC-04 | **创建报名订单** | POST /api/enrollment | 10% | **核心 P95 ≤3s** |
| SC-05 | 订单详情 | GET /api/enrollment/{id} | 8% | P95 ≤1s |
| SC-06 | 学员详情 | GET /api/student/{id} | 7% | P95 ≤1s |
| SC-07 | **财务日报查询** | GET /api/report/finance/daily | 5% | **核心 P95 ≤5s** |
| SC-08 | 小程序我的课表 | GET /api/wx/schedule/mine | 10% | P95 ≤1.5s |
| SC-09 | 教师考勤 | POST /api/teacher/attendance | 5% | P95 ≤2s |
| SC-10 | 新增学员 | POST /api/student | 5% | P95 ≤1.5s |

### 3.2 核心场景脚本设计

#### SC-04 · 创建报名订单（最重要）
```
线程组：jp@gc - Ultimate Thread Group
  - 阶段1：100并发 0-5min 爬升 → 持续5min
  - 阶段2：300并发 爬升5min → 持续10min
  - 阶段3：500并发 爬升5min → 持续15min
  - 阶段4：释放至0 5min

前置：CSV 变量读取已造好的 50000 学员ID、课程ID、班级ID
取样器：
  1. HTTP Header Manager（带动态 token）
  2. ① 登录（仅每个线程启动时一次，Once Only Controller）
       提取 token → 正则/jmespath 提取器
  3. ② 创建报名订单 POST
       Body 数据中用 ${studentId}/${courseId}/${__counter(TRUE,hour_)}
       - JSON 断言：code=0, data.payAmount=1800
       - 响应断言："已支付"或"待支付"
       - 响应时间断言：≤3000ms
  4. ③ 查询订单详情 GET （50% 概率，If Controller）
  5. ④ 随机思考时间 300-800ms Gaussian Random Timer
```

#### SC-07 · 财务日报查询（报表慢 SQL 热点）
```
线程组：Stepping Thread Group (50 → 100 → 150)
参数：date 随机取近30天中一天
检查点：
  - data.totalAmount = 数据库 sum(pay_amount) WHERE pay_time=date，断言脚本（JDBC Request）
DB 对比：同时建 JDBC 连接池，执行相同 SQL 对比响应时间
慢 SQL：开启 slow_log=1s，压测后汇总 Top10 用 Explain 分析
```

### 3.3 并发一致性场景（防超卖/幂等）
| 场景 | 线程数 | 期望结果 |
|------|--------|----------|
| 同一优惠券，1000 个用户同时领取，总共只有 50 张券 | 1000 × 1 循环 | 实际发放 ≤ 50 |
| 同一个订单，500 个线程同时提交（相同 requestId） | 500 × 1 | 最终只创建 1 个订单 |
| 缴费接口回调：同一个订单，200 个线程同时回调成功 | 200 × 1 | 课时 +1 次 不出现多加 |
| 班级 30 个名额 300 人同时报名 | 300 × 1 | 成功 30 人排队 270 人 |

## 四、监控指标清单

### 4.1 应用层
| 指标 | 采集方式 | 告警阈值 |
|------|----------|----------|
| TPS、RT（平均/P90/P95/P99） | JMeter Listener / Backend Listener to InfluxDB | P95 超目标值×120% |
| 错误率 | JMeter 断言结果 | > 0.1% |
| 吞吐量（字节/秒） | JMeter | |
| HTTP 状态码分布（2xx/4xx/5xx） | JMeter 汇总 | 5xx > 0 即告警 |

### 4.2 系统层
| 指标 | 采集方式 | 阈值 |
|------|----------|------|
| CPU 使用率（user/sys/iowait） | node_exporter / nmon | >80% 持续 3min |
| 内存使用率（物理+SWAP） | nmon / free -m | >85% 或 SWAP>0 |
| 磁盘 IO（rMB/s wMB/s %util） | iostat -x 1 | %util >90% |
| 磁盘空间（df -h） | crontab | >85% |
| 网络收发包流量 | sar -n DEV | 打满带宽 70% 告警 |
| 负载均衡（LB 节点请求分布） | Nginx status | 偏差>15% 说明不均 |

### 4.3 中间件 & 数据库
| 组件 | 指标 |
|------|------|
| JVM | 堆/非堆内存、YGC/FullGC 次数耗时、线程数（BLOCKED状态）、死锁、方法热点（Arthas trace） |
| Redis | 命中率、连接数、内存碎片率、rdb_bgsave 耗时、慢日志 >10ms |
| MySQL | QPS/TPS、慢查询（>1s）、Innodb Buffer Pool Hit、锁等待、死锁、主从延迟 |
| RabbitMQ | 队列堆积、消费速率、未 ACK 消息 |
| Nginx | active connections、request_time upstream_response_time |

## 五、测试轮次计划

| 轮次 | 日期 | 目标 |
|------|------|------|
| 第 0 轮：基准测试 | 07-15 | 单用户跑通所有场景，记录 baseline |
| 第 1 轮：负载测试 100/300 并发 | 07-17 | 验证功能正确性 + 初步性能数据 |

| 第 3 轮：压力测试 800/1000 并发 × 10min | 07-23 | 找到系统瓶颈点 |
| 第 4 轮：开发调优后 回归测试 | 07-28 ~ 08-01 | 至少 2 轮调优 → 回归 |
| 第 5 轮：稳定性测试 70% 负载 × 24h | 08-04 | 是否内存泄漏、连接泄漏 |
| 第 6 轮：异常演练（节点宕机/网络抖动） | 08-06 | 高可用验证 |

## 六、风险与应对
| 风险 | 概率 | 应对 |
|------|------|------|
| 性能环境资源不足 达不到生产量级 | 中 | 性能结果按资源比例线性换算；或申请临时扩容 |
| 数据造数不到位 索引命中率与生产差 | 高 | 严格按照生产分布造数据；DBA 审查数据分布直方图 |
| 压测影响 SIT 联调 | 低 | 使用完全独立的 PERF 环境，域名和 DB 都隔离 |
| 开学季突发流量 > 预估 | 中 | 压测到目标 1.5 倍；给出限流降级方案 |
