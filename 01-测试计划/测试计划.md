## 1. 项目概述

### 1.1 项目背景
某教育科技有限公司面向 K12 培训机构打造一站式教务管理 SaaS 平台，支持多校区、多角色管理，覆盖招生-报名-缴费-排课-教学-评价-财务全链路。本次 V2.0 版本上线目标：
- 替换原 V1.0 老旧架构，性能提升 5 倍以上
- 新增 AI 智能排课、微信小程序学员端、教师移动 H5
- 对接广西本地教育局"双减"课时上报接口

### 1.2 项目干系人
| 角色 | 姓名/部门 | 职责 |
|------|-----------|------|
| 产品经理 | 产品部 · 李经理 | PRD、需求变更、验收 |
| 项目经理 | PMO · 张经理 | 项目排期、风险、跨部门协调 |
| 开发负责人 | 研发部 · 王工 | 版本迭代、代码质量 |
| 测试负责人 | 测试部 · 苏绍彰 | 测试全流程、质量把控 |
| 客户方对接 | 运营部 · 陈老师 | UAT、业务确认、培训 |

### 1.3 系统架构简述
- **前端**：Vue3 + Element Plus（后台）、UniApp（小程序）、Vue3 + Vant（H5）
- **后端**：SpringBoot 2.7 + MyBatis-Plus + Redis + RabbitMQ
- **数据库**：MySQL 8.0（分库分表 ShardingSphere）
- **文件存储**：腾讯云 COS
- **部署**：CentOS 7 + Docker + Nginx + Jenkins CI/CD

## 3. 测试策略

### 3.1 总体测试策略
```
需求评审 → 测试计划 → 用例设计 → 用例评审
    ↓
冒烟测试 → 第一轮功能测试(含接口) → 缺陷修复与回归
    ↓
第二轮功能测试 → 性能测试 → 兼容性测试 → UAT
    ↓
上线评审 → 生产冒烟 → 线上跟踪
```

### 3.2 测试方法说明
| 方法 | 说明 | 适用场景 |
|------|------|----------|
| 等价类划分 | 输入域划分有效/无效等价类 | 表单输入、查询条件 |
| 边界值分析 | min-1 / min / min+1 / max-1 / max / max+1 | 金额、数量、日期、长度 |
| 判定表法 | 多条件多组合业务规则 | 优惠计算、排课冲突检测 |
| 场景法 | 基本流 + 备选流设计业务场景 | 报名缴费全流程、转课退费 |
| 正交实验法 | 多因素多水平筛选用例 | 报表多维度筛选查询 |
| 错误推测法 | 经验推测易错点 | 并发、异常流程、边界数据 |

### 3.3 缺陷等级定义

| 等级 | 定义 | 示例 | 修复时限 |
|------|------|------|----------|
| 致命 (Critical) | 系统崩溃、数据丢失、核心业务无法使用 | 缴费后订单丢失、登录 500 | 24h |
| 严重 (Major) | 核心功能异常、数据错误但有补救 | 报表金额计算错误、越权访问 | 48h |
| 一般 (Normal) | 一般功能缺陷、有替代方案 | 表单校验缺失、UI 错位 | 72h |
| 轻微 (Minor) | 建议优化、UI 瑕疵 | 提示文案错误、按钮位置不佳 | 下个版本 |
| 建议 (Suggestion) | 用户体验优化建议 | 操作流程建议 | 产品评审决定 |

## 5. 测试用例设计规范

### 5.1 用例编写规范
- **用例编号**：`ZW-EMS-{模块}-{序号}` 示例：ZW-EMS-M04-0001
- **用例标题**：动词开头，结果明确，不超过 30 字
- **前置条件**：操作前必须满足的环境/数据条件
- **操作步骤**：1、2、3… 编号，每步单一操作
- **预期结果**：可见结果 + 数据变化 + 日志/接口状态
- **优先级**：P0（冒烟必过）/ P1（核心功能）/ P2（重要功能）/ P3（边缘）

### 5.2 用例设计方法使用原则
| 模块 | 主要方法 | 辅助方法 |
|------|----------|----------|
| 学员/课程表单 | 等价类 + 边界值 | 错误推测 |
| 报名缴费计算 | 判定表 + 场景法 | 边界值 |
| 智能排课冲突 | 判定表 + 正交实验 | 错误推测 |
| 报表查询 | 正交实验 + 场景法 | 边界值 |
| 接口测试 | 等价类 + 鉴权场景 | 边界值 |

### 5.3 用例覆盖率要求
- 需求点覆盖率 ≥ 98%
- P0/P1 用例执行率 = 100%
- P2/P3 用例执行率 ≥ 90%

## 7. 缺陷管理流程

### 7.1 缺陷生命周期
```
新建(New) → 指派(Assigned) → 已确认(Confirmed) → 修复中(In Progress)
    ↓
待验证(Resolved) → 验证通过(Verified) → 关闭(Closed)
                    ↓ 验证失败
                重新打开(Reopened) → 回到修复中
```

### 7.2 缺陷管理工具
- 主工具：**禅道 18.x**（缺陷 ID 自动生成、关联需求、关联用例）
- 流程要求：每条缺陷必须包含【复现步骤 + 实际结果 + 期望结果 + 截图/日志 + 发生环境】
- 每日 9:30 缺陷 triage 会议，未关闭缺陷逐个 review
